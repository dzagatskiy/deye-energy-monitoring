# ADR 0002: Файлове сховище замість SwiftData

**Статус:** прийнято, 2026-11-23. Замінює пункт 2.4 початкового плану (SwiftData).

## Контекст

Телеметрію пишуть три процеси: застосунок, `BGAppRefreshTask` і віджет. Об'єм невеликий: Deye Cloud дає кадр приблизно кожні 5.7 хв, тобто близько 250 вимірів на добу на інвертор, а за 90 днів це ~22 тис. записів. Відключення, енергія та статистика перераховуються з сирих вимірів (`OutageTracker` — чиста функція), тому окремі таблиці для них не потрібні.

## Рішення

`TelemetryStore` (EnergyCore, лише Foundation) зберігає JSON у контейнері App Group:

```
<AppGroup>/EnergyMonitor/
  samples/<deviceSn>/<yyyy-MM-dd UTC>.json   // масив TelemetrySample, відсортований, без дублікатів
  settings.json                              // AccountSettings (без секретів)
  sync-<deviceSn>.json                       // час останнього завантаження історії
  snapshot-<deviceSn>.json                   // EnergySnapshot для віджета
```

- Запис: прочитати файл доби → злити → `SampleSeries.normalize` (сортування, дедуплікація, локальний вимір має пріоритет) → атомарна заміна файлу.
- Ретеншн: файли старші 90 днів видаляються.
- Секрети (AppSecret, SHA-256 пароля, токен) лежать у Keychain з access group = App Group і доступні після першого розблокування.

## Чому не SwiftData

- Одночасний доступ застосунку й розширення до одного SQLite-сховища SwiftData потребує обережності, а помилки міграції схеми виходять дорожчими за вигоду при ~250 записах на добу.
- Файлове сховище тестується `swift test` без Xcode і симулятора.
- Дані й так перераховуються з сирих вимірів, запити до бази не потрібні.

## Наслідки

- Якщо два процеси одночасно зливають одну й ту саму добу, виграє останній запис і кілька вимірів можуть загубитися. Наступне завантаження історії їх поверне, бо дані в Deye Cloud лишаються.
- Якщо обсяг суттєво зросте (локальне опитування кожні 15 с означає ~5.7 тис. вимірів на добу), варто проріджувати локальні виміри перед записом або перейти на SQLite.

## Доповнення 2026-11-24: кеш запитів до Deye Cloud

Сховище вище — це кеш *даних*: виміри, налаштування й знімки для віджета переживають перезапуск і доступні офлайн. Додано ще кеш *запитів*, щоб не питати Deye про те, чого там ще немає.

`FetchCachePolicy` (у `RefreshService`) вирішує, чи йти по `/device/latest`:

1. Минуло менше **60 с** від останнього успішного запиту для цього інвертора, хоч би хто його робив (застосунок, віджет, фонове завдання) — беремо збережене.
2. Новий кадр Deye ще не мав надійти (останній вимір + **350 с**, медіана 343 с) — беремо збережене, але не довше **7 хв** від запиту.
3. Інакше — запит.

- Час останнього запиту (`SyncState.lastSuccessAt`) лежить в App Group, тому кеш **спільний для всіх процесів**: віджет після застосунку не дублює запит.
- «Потягнути, щоб оновити» обходить кеш (`.bypass`), але не обмежувач 60 запитів/хв.
- Кеш не скидає останню помилку: якщо запиту не було, невідомо, чи зв'язок відновився.
- На огляді видно обидва моменти: «Дані Deye» — час виміру, «Перевірено» — час останнього запиту.

Ефект (тест `requestsPerFrame`): опитування щохвилини за 30 хв дає 6 запитів, по одному на кожен кадр Deye, замість 30. Затримка появи нового кадру — до одного інтервалу опитування.
