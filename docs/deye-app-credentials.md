# AppId / AppSecret: як отримати й де зберігати

Дата аналізу: 2026-11-24. Джерела: офіційний `deye-openapi-client-sample-code` (README) і `deyecloud-skills/deye-openapi-quickstart` (SKILL.md, v261019). Сторінки developer.deyecloud.com рендеряться через JS і автоматично не читаються.

## Що відомо

| Питання | Факт |
|---|---|
| Як отримати ключі | Акаунт Deye Cloud → developer.deyecloud.com/app → створити Application → AppId і AppSecret на сторінці застосунку |
| API для створення застосунку чи отримання ключів | **Немає.** Єдиний API тут — `/account/token`, і він уже потребує AppId/AppSecret |
| Модерація застосунку | Не описано |
| Токени для чужих акаунтів (один AppId на багатьох користувачів) | Не описано. OAuth / authorization code для сторонніх користувачів немає |
| Квоти | Неофіційно: ~60 запитів/хв і ~100 тис./міс **на застосунок** |
| Токен | Живе 60 днів, нові токени не скасовують старі, токен скасовується при зміні пароля. Окремого способу оновлення немає, лише новий вхід з email і паролем |

## Варіанти

| Варіант | Кроків для користувача | Оцінка |
|---|---|---|
| **A. Повністю автоматично через API** | 0 | Неможливо: API для цього немає |
| **B. Напівавтоматично через WKWebView**: користувач входить на портал у вбудованому браузері, застосунок зчитує ключі зі сторінки (або натискає «створити») | 2–3 | Технічно можливо, але крихко. Розмітка порталу не документована й зміниться без попередження, а застосунок бачив би вхід користувача на сторонньому сайті. Не реалізовано |
| **C. Напівручний майстер** *(реалізовано)*: 3 кроки, кнопка «Відкрити портал», «Вставити» розпізнає ключі в будь-якому скопійованому тексті | 3 | Надійно, працює з будь-якою версією порталу |
| **D. Ключі вбудовані в збірку** *(реалізовано, опційно)*: `Config/Secrets.xcconfig` → Info.plist → застосунок питає лише email і пароль | 0 | Лише для **власної** збірки. Ключі можна витягти з .ipa, і всі користувачі ділили б одну квоту. Чи може один AppId працювати з чужими акаунтами, не підтверджено |

## Що зроблено

- **Майстер ключів** (`App/AuthViews.swift → DeveloperKeysView`): показується при першому запуску, якщо ключів немає, і доступний з налаштувань і з екрана входу.
  - `PasteButton` вставляє з буфера без системного запиту на доступ до буфера.
  - `DeyeAppCredentialsParser` (EnergyCore, з тестами) розпізнає `App ID: …`, `AppId=…`, JSON, рядки `DEYE_APP_ID = …` і просто значення за формою: AppId — 10–20 цифр, AppSecret — 32 hex-символи.
  - Перед збереженням ключі перевіряються локально (`isPlausible`). По-справжньому їх перевіряє вхід, бо Deye не має запиту, який перевіряв би ключі без акаунта.
- **Вхід відокремлено від ключів** (`LoginView`): email, пароль, регіон і перемикач **«Запам'ятати пароль»** (за замовчуванням увімкнено).
  - Увімкнено: у Keychain зберігається SHA-256 пароля, застосунок і віджет самі отримують новий токен.
  - Вимкнено: зберігається лише токен (~60 днів). Клієнт користується ним до кінця терміну, а потім повертає `loginRequired`, і застосунок показує екран входу з уже заповненим email.
- **Keychain** розділено на три записи: `app` (ключі розробника), `account` (email і, за бажання, SHA-256 пароля), `token`. Старий спільний запис `credentials` мігрується автоматично (перевірено на реальних даних у симуляторі).
- **Налаштування → Deye Cloud:** акаунт, чи збережено пароль, «Забути пароль», «Ключі розробника» (AppId показано як `…1234`), «Вийти з акаунта». Після виходу ключі розробника лишаються.

- **«Швидкі команди»** (`App/DeyeKeysIntents.swift`): дія «Зберегти ключі Deye» приймає текст сторінки порталу (Safari → Поширити), буфер обміну чи нотатку й зберігає ключі тим самим парсером. Це варіант C, але з одного дотику на сторінці порталу. Налаштування: [shortcuts.md](shortcuts.md).

## Як вбудувати ключі у власну збірку

```bash
cp Config/Secrets.example.xcconfig Config/Secrets.xcconfig   # файл у .gitignore
# вписати DEYE_APP_ID і DEYE_APP_SECRET, зібрати
```

Ключі, збережені в застосунку, мають пріоритет над вбудованими.
